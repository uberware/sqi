# Accepted divergences between sqi's Go evaluator and the OpenJD reference
# implementation, in the same spirit as test/conformance/baseline-expr.txt: a
# case listed here is known to disagree, and the disagreement has been
# adjudicated rather than ignored.
#
# Format: the comment lines immediately above an entry are its reason, and the
# entry itself is a case id from corpus.txt — "<target> :: <expression>",
# exactly as the failure output prints it. A blank line separates entries. An
# entry with no reason above it is a hard error, and so is an entry naming a
# case that is not in the corpus.
#
# THE SPEC OUTRANKS THE REFERENCE. openjd-expr is Beta (0.x, breaking changes
# permitted in minor bumps), so an entry here may record either a genuine gap
# in sqi or a case where sqi is right and the reference is wrong. Say which.
#
# A baselined case that STOPS diverging also fails the test. That is deliberate
# — this file is a list of open questions, and one answering itself is worth
# knowing about.

# ── sqi is right: the reference mishandles and/or under a target type ────────
#
# Three entries, one root cause, and the evidence is that the reference gets
# all three RIGHT when no target type is supplied:
#
#   false or 'fallback'  ->  'fallback' : string
#   null or 7            ->  7 : int
#   true and 0           ->  0 : int
#
# Supplying a target type changes the ANSWER, not merely its coercion. With
# target=string, "false or 'fallback'" returns "false" — the operand the spec
# says is discarded. The reference appears to type and/or statically as a union
# of both operand types and push the target coercion through that union, which
# both loses the short-circuit and, when a member cannot coerce (bool->int,
# nulltype->int), rejects an expression that has a perfectly good value.
#
# Spec section 2.1.6 is unambiguous, and states the rule as a value rule rather
# than a typing rule:
#
#   a and b   If a is null or false, return a; otherwise evaluate and return b
#   a or b    If a is null or false, evaluate and return b; otherwise return a
#
# and adds that they "are value-returning: they return one of their operands,
# not necessarily a bool". sqi evaluates the operator first and coerces the
# operand it actually returned, which is what those rules describe.
#
# Worth reporting upstream. Until then these stay as documentation that the
# disagreement is known and which side the spec is on.

# and/or under a target type: the reference errors, sqi returns 0 per 2.1.6.
int :: true and 0

# and/or under a target type: the reference returns the DISCARDED operand
# ("false"), sqi returns 'fallback' per 2.1.6.
string :: false or 'fallback'

# and/or under a target type: the reference errors on nulltype->int, sqi
# returns 7 per 2.1.6 — the null operand is the one being discarded.
int :: null or 7

# ── sqi is right: float exponent rendering ──────────────────────────────────
#
# sqi renders 1e-05, the reference renders 1e-5. Python's repr — which sqi's
# formatFloat deliberately reproduces, and which the spec's own float examples
# follow — gives 1e-05, so sqi matches the language the spec defines itself as
# a subset of and the reference does not. Note the reference is not internally
# consistent about this either: it renders the positive exponent as 1e+16,
# keeping both the sign and the two-digit field it drops here.
#
# The spec does not state a rendering for computed floats outside the fixed
# notation window, so this is a real ambiguity rather than a plain bug. If it is
# ever settled against sqi, the change is confined to formatFloat in value.go.

# Float exponent rendering: sqi gives 1e-05 (Python's repr), reference 1e-5.
float :: 0.00001 * 1.0

# ── sqi is right: the reference cannot coerce anything to an explicit ANY ────
#
# Every case in this block fails in the reference with "Cannot coerce <T> to
# any" — and this is not list-specific. The identical failure reproduces for
# plain scalars: evaluate_expression("1", target_type=ExprType("any")) raises
# "Cannot coerce int to any", while evaluate_expression("1") with no
# target_type at all returns 1 : int with no error. The Recommended Library
# Interface's ExprType table defines ANY as "Unconstrained type (matches
# anything)", and the ExprValue section is explicit that "ANY, UNION, and
# UNRESOLVED are type-level constructs used during type checking. They do not
# appear as the type of a concrete ExprValue at runtime — values always have a
# specific concrete type." A target type of ANY is therefore a no-op
# constraint: the result should keep its own concrete type, exactly as it
# does when no target type is given at all. The reference instead treats an
# explicit ANY target as if it were a normal concrete coercion target with its
# own conversion rules, which were never written, so every value — scalar or
# list — is rejected. sqi returns the value unchanged (in its own concrete
# type) for an ANY target, per that definition.
#
# This is one root cause, confirmed independently for scalars, list literals,
# and list-operator results; each entry below lists its specific expression so
# the baseline stays searchable, but the reason is this paragraph for all of
# them.

# ANY target coercion: reference errors "Cannot coerce list[int] to any" on
# every list value, scalar or not — see the shared explanation above.
any :: [1, 2, 3]

# ANY target coercion, empty list — reference errors on list[nulltype] too.
any :: []

# ANY target coercion, single-element list.
any :: [42]

# ANY target coercion; also exercises the trailing-comma grammar.
any :: [1, 2, 3,]

# ANY target coercion, list[string].
any :: ['a', 'b']

# ANY target coercion, list[bool].
any :: [true, false]

# ANY target coercion, list[float] after 1.2.6's int/float inference.
any :: [1, 2.0, 3]

# ANY target coercion, list[list[int]].
any :: [[1, 2], [3, 4]]

# ANY target coercion, list[list[float]].
any :: [[1], [2.0]]

# ANY target coercion, list built from evaluated sub-expressions.
any :: [1 + 1, 2 * 2]

# ANY target coercion, list concatenation result (section 2.1.3).
any :: [1, 2] + [3, 4]

# ANY target coercion, list concatenation with int/float unification.
any :: [1] + [2.0]

# ANY target coercion, list[nulltype] + list[int] concatenation.
any :: [] + [1]

# ANY target coercion, list repetition (section 2.1.3).
any :: [0] * 3

# ANY target coercion, list repetition.
any :: [1, 2] * 2

# ANY target coercion, list repetition by zero.
any :: [1] * 0

# ── sqi is right: the reference mistypes subscript/slice under a target type ─
#
# Every subscript and slice case below fails, and the cause is not specific to
# lists, to ANY, or to any one target type: it reproduces with a plain `int`
# target, with a matching `list[int]` target, and with a matching `string`
# target alike, and it disappears completely when target_type is omitted.
# Reproduced directly against openjd-model 0.11.1:
#
#   evaluate_expression("[10,20,30][0]", target_type=ExprType("int"))
#     -> Cannot coerce list[int] to int      (WRONG: should be 10 : int)
#   evaluate_expression("[10,20,30][0]", target_type=ExprType("list[int]"))
#     -> Cannot coerce int to list[int]      (WRONG: the *opposite* mismatch)
#   evaluate_expression("[10,20,30][0]")     -> 10 : int   (correct, no target)
#   evaluate_expression("X[1:4]", target_type=ExprType("list[int]"))
#     with X bound to [10,20,30,40,50] : list[int]
#     -> Cannot coerce int to list[int]      (WRONG: a slice returns a list)
#
# The reference's static type-checking pass for a target type does not model
# what `__getitem__` (section 2.1.7) or slicing (section 2.1.8) does to the
# static type of a postfix expression — a subscript narrows list[T] to T, a
# slice keeps list[T] (or keeps string as string) — and substitutes some other
# type into the check instead, which is why the two experiments above report
# opposite, self-contradictory mismatches for the identical expression. Spec
# sections 2.1.7 and 2.1.8 define subscript and slice purely in terms of the
# operand types, with no carve-out for the presence of a target type, and
# section 1.3.1 says a target type merely "guides implicit type coercion" — it
# does not license the checker to compute a different result type. sqi threads
# the target type through evaluation and coerces the actual computed value,
# which is what these sections require.

# Subscript under a target type: see the shared explanation above.
any :: [10, 20, 30][0]

# Subscript under a target type.
any :: [10, 20, 30][2]

# Subscript under a target type, negative index.
any :: [10, 20, 30][-1]

# Subscript under a target type, negative index.
any :: [10, 20, 30][-3]

# Subscript under a target type, chained on a nested list.
any :: [[1, 2], [3, 4]][1][0]

# Subscript under a target type, string character access.
string :: 'hello'[0]

# Subscript under a target type, negative string index.
string :: 'hello'[-1]

# Slice under a target type.
any :: [10, 20, 30, 40, 50][1:4]

# Slice under a target type, omitted start.
any :: [10, 20, 30, 40, 50][:3]

# Slice under a target type, omitted stop.
any :: [10, 20, 30, 40, 50][2:]

# Slice under a target type, full copy.
any :: [10, 20, 30, 40, 50][:]

# Slice under a target type, stepped.
any :: [10, 20, 30, 40, 50][::2]

# Slice under a target type, reversed.
any :: [10, 20, 30, 40, 50][::-1]

# Slice under a target type, start/stop/step all given.
any :: [10, 20, 30, 40, 50][0:5:2]

# Slice under a target type, negative start.
any :: [10, 20, 30, 40, 50][-3:]

# Slice under a target type, negative stop.
any :: [10, 20, 30, 40, 50][:-2]

# Slice under a target type, stop past the end (Python-style clamping, 2.1.8).
any :: [10, 20, 30, 40, 50][1:99]

# Slice under a target type, start past the end.
any :: [10, 20, 30, 40, 50][99:]

# Slice under a target type, start after stop (empty result).
any :: [10, 20, 30, 40, 50][3:1]

# Slice under a target type, string slice.
string :: 'hello'[1:3]

# Slice under a target type, reversed string slice.
string :: 'hello'[::-1]

# Slice under a target type, string slice with stop past the end.
string :: 'hello'[1:99]

# ── sqi is right: the reference requires an exact element type for 'in' ──────
#
# `2.0 in [1, 2, 3]` errors in the reference with "Cannot use 'in' operator
# with list[int] and float", and the same happens in reverse: `1 in
# [1.0, 2.0, 3.0]` also errors there. Section 2.1.3's signature is
# `__contains__(list: list[T], item: T) -> bool`, but membership is
# fundamentally an equality test, and section 1.2.5 is explicit that `int` vs
# `float` is "Numeric comparison (e.g., 5 == 5.0 is true)" rather than an
# error. 2.0 equals the int 2 by that rule, and 2 is an element of the list, so
# `2.0 in [1, 2, 3]` must be true. The reference appears to require the item's
# static type to unify exactly with T before considering the membership test
# at all, instead of falling back to the language's own cross-type equality
# rule element by element. sqi's containsElem uses that same cross-type
# equality (internal/openjd/expr/ops.go), consistent with 1.2.5 and with what
# `in` needs to mean.

# 'in' with a float item against a list[int]: reference rejects the mixed
# types outright instead of applying 1.2.5's int/float equality rule.
bool :: 2.0 in [1, 2, 3]

# ── known gap in sqi: list-of-strings rendering is not the final form ────────
#
# `[1, 2]` coerced to `list[string]` computes correctly on both sides — sqi's
# elements are genuinely type=string, value="1"/"2" internally (verified
# directly against the coercion step, not inferred from the printed form) —
# but the two sides print the result differently: sqi renders `[1, 2]` (no
# quotes around string elements), the reference renders `["1", "2"]`
# (JSON-quoted). The spec documents to_string() as doing exactly that for
# lists: "Lists are converted to JSON" (Recommended Library Interface,
# ExprValue.to_string()). sqi's Value.String() is explicitly commented as a
# diagnostics/test rendering rather than the definitive form —
# internal/openjd/expr/value.go says outright that "the definitive form used
# when interpolating a value back into a template is sub-project E's to fix."
# This is a known, already-tracked gap rather than a fresh one: recorded here
# so the oracle stays green in the meantime, not as a claim that sqi's current
# rendering is correct or final.

# List-of-strings rendering: sqi prints unquoted elements ([1, 2]), the
# reference prints JSON-quoted elements (["1", "2"]); both sides agree on the
# actual values and on the list[string] type. Deferred to sub-project E per
# value.go's own comment on Value.String().
list[string] :: [1, 2]
