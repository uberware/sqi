#
# Differential-test corpus for `make test-expr-oracle`. Each case is evaluated
# by BOTH sqi's Go evaluator and the OpenJD reference implementation, and the
# two results are compared.
#
# Format: one case per line, a TARGET TYPE and an EXPRESSION separated by a
# single TAB. Blank lines and lines starting with "#" are ignored. A tab is the
# separator because every other candidate appears inside real cases: spaces are
# everywhere, and "|" is a union in the target type ("int | string").
#
# SCOPE: expressions that sub-projects A, B1, B2, B3 and C1 actually implement —
# scalar operators, the coercion matrix, comparison chains, conditionals,
# and/or, list literals and their type inference, list operators, subscripts,
# slices, list comprehensions, and C1's general, validation, math and list
# functions. The string, regular-expression, repr_* and path families are
# sub-projects C2, C3 and C4 and are not here yet.
#
# TARGET TYPES MUST BE UNIONS FOR ANY CASE CONTAINING A CALL, A SUBSCRIPT OR A
# SLICE, and this is not a style preference. The reference implementation
# applies the supplied target_type to a construct's OPERANDS as well as to its
# result — reported upstream as openjd-rs#291, and observed here on call
# arguments, subscript receivers and indices, slice bounds, and the operand
# and/or discards. So "floor(3.7)" with the target "int" fails there, because
# the target lands on the 3.7. Give the target a member for every operand and
# the pushdown becomes harmless:
#
#   floor(3.7)               int | float
#   sum([1,2,3])             int | list[int]
#   range(5)                 list[int] | int
#   'hello'[1:3]             string | int | nulltype
#
# A case written with the obvious single target produces a divergence that
# looks real and is not. If you add a case and it diverges, check the target
# before reaching for baseline.txt.
#
# A handful of cases are in deliberately and are expected to diverge. They earn
# their place by DOCUMENTING a gap or a disagreement rather than leaving it
# implicit, and each is listed in baseline.txt with the reason. Do not delete a
# case to make the target green.

#
# The EMPTY list on either side of an ordering operator. Section 1.2.5 says the
# shorter list is less when all compared elements are equal, and section 1.2.6
# rule 6 makes list[nulltype] convertible to list[T] for any T — so both orders
# must answer, and sqi's did not: "[] < [1]" was a type error while "[1] < []"
# was false, because the empty literal PINNED the shared element-type variable
# to nulltype when it came first. The reference agrees with the fixed behaviour
# on every line here, including the last, where the empty list is nested one
# level deeper than the other operand and there is no conversion at all.
#
# BOTH ORDERS of every nesting depth, which is the part this section originally
# missed: the nested case was pinned in one direction only ("[[]] < [[1]]"), and
# "[[1]] < [[]]" was still a type error for want of the mirror-image rule, with
# nothing here to notice. A corpus row that exists in one direction only cannot
# see an asymmetric fix.
bool	[] < [1]
bool	[1] < []
bool	[] <= [1]
bool	[] < []
bool	[] <= []
bool	[[]] < [[1]]
bool	[[1]] < [[]]
bool	[[1]] > [[]]
bool	[[]] <= [[1]]
bool	[[]] < [1]
#
# Section 2.1.4's compatible pairs (int/float, string/path) applied
# ELEMENTWISE, which list ordering rejected outright until this wave: sqi
# answered "unsupported operand types" for every row here, on the reading that
# section 1.2.5's elementwise rule required an exact element-type match. It does
# not say that, and 2.1.4 says operands "may differ for compatible pairs" — so
# these now order rather than erroring, and every row agrees with the reference.
# The string/path half cannot be written here (path has no literal syntax and
# the corpus supplies no symbol table); it is covered by
# TestListOrdering_CompatiblePairs, where the reference DISAGREES on the mixed
# path/string rows by answering false in both directions.
bool	[1] < [1.0]
bool	[1.0] < [1]
bool	[1] <= [1.0]
bool	[1] >= [1.0]
bool	[1, 2] < [1.0, 3.0]
bool	[[1]] < [[1.0]]
#
# The fence: a pair that is NOT one of section 2.1.4's compatible pairs is
# still an error on both sides, at either nesting depth.
bool	['a'] < [1]
bool	[1] < ['a']
bool	[1] < [[]]

# range_expr -> string is a NON-DESTRUCTIVE coercion (section 1.2.3) that the
# spec says "produces canonical form like '1-5'" (2026-02
# Expression-Language.md line 843), and section 2.1.2's __add__(range_expr,
# string) row says the same thing explicitly: "range_expr converted to
# canonical string form" (line 1189). Unlike the bare range_expr VALUE cases
# above (whose target admits range_expr, so no coercion occurs and the text
# is genuinely unspecified — see baseline.txt), these three force the
# coercion by excluding range_expr from the target or by using the string
# operator, so the spec's "canonical form" wording is in force. sqi does not
# canonicalize here; see baseline.txt for the known-gap entry.

# ── coverage recovered from the openjd-rs#291 target pushdown ────────────────
#
# Each case below is a TWIN of an entry in baseline.txt. The baselined original
# keeps its narrow target and stays baselined: it is the evidence for the
# upstream defect, and it is designed to fail loudly the day that defect is
# fixed. The twin supplies the union target the rule above describes, which
# makes the pushdown harmless and turns the case into live differential
# coverage — coverage sub-project B2 recorded as unobtainable.
#
# Do not "consolidate" the two. Deleting an original orphans its baseline
# entry, which is a hard error, and loses the record of why these targets look
# strange.

# Subscript twins (baseline target was "any" — unusable on its own, see
# baseline.txt's shared explanation for the subscript/slice section; the
# reference also cannot evaluate against a bare "any" target at all, a
# separate, unrelated limitation documented next to the list-literal cases
# above). Each twin's target is the actual result type unioned with the
# receiver's type and int, per the subscript rule.

int | list[int]	[10, 20, 30][2]
int | list[int]	[10, 20, 30][-1]
int | list[int]	[10, 20, 30][-3]

string | int	'hello'[-1]

# second case is doubly nested — the outer body is itself a comprehension, so
