# Accepted OPERATION-COUNT divergences between sqi's Go evaluator and the OpenJD
# reference implementation, for section 1.3.10's operation-bounded evaluation.
#
# Kept separate from baseline.txt deliberately. The two failure modes are
# independent -- a case may agree on VALUE and diverge on COUNT -- and the
# three-direction rule (an unlisted divergence is a regression, a listed case
# that stops diverging is stale, an entry matching no live result is orphaned)
# has to hold separately for each. One file could not express that.
#
# Counts are compared ONLY on cases whose values already agree. A case whose
# value diverges is already reported and already baselined; comparing its count
# too would report one root cause twice.
#
# Format: the comment lines immediately above an entry are its reason, and the
# entry itself is a case id from corpus.txt -- "<target> :: <expression>",
# exactly as the failure output prints it. A blank line separates entries. An
# entry with no reason above it is a hard error.
#
# THE SPEC OUTRANKS THE REFERENCE. Section 1.3.10 states the counting rules
# precisely, which is what makes counts comparable at all -- but openjd-expr is
# Beta and has known counting defects (C2 recorded center('ab', -3) failing with
# "operation count (72057594037927938) exceeded limit"). An entry here may record
# either a genuine gap in sqi or a case where sqi is right. Say which.

# ── sqi is right: the reference over-counts ordering, equality and "not" ────
#
# RFC 0005's AST-transformation table (section "AST Transformation to Uniform
# Function Calls") converts every ordering comparison (<, <=, >, >=), both
# equality operators (==, !=) and "not" into a __lt__/__le__/.../__not__ call.
# Section 1.3.10 rule 1 ("every function call counts as 1 operation") is the
# whole charge for each of these whenever its operands are SCALARS: nothing
# iterates a list and nothing processes a string byte-for-byte, so rules 2
# and 3 have nothing to charge. The reference nevertheless measures 2 for
# every ordering comparison, for "not True" and for scalar equality -- a flat
# +1 with no textual home, and the divergence every entry below records.
#
# A CHAINED comparison ("1 < 2 < 3") is section 1.3.6's single Compare node,
# evaluated as one short-circuiting unit; the reference's extra +1 is paid
# ONCE for the whole chain, not once per link -- confirmed by "1 < 2 < 3"
# measuring only 1 more than sqi's 2 (which already charges rule 1 once per
# link), not 2 more.
#
# CORRECTION (final whole-branch review, sub-project E1). This header
# previously extended the rule-1-only claim to the LIST/LIST ordering row as
# well, arguing "the list/list row of an ordering comparison is not the
# 'list/range equality comparisons' rule 2 names by name -- that is a
# distinct, separately-costed operation". That is overturned. doc.go settles
# the disagreement between the two specification documents over whether rule
# 2's enumeration is open or closed (the wiki says "such as", RFC 0005 says
# "This applies to:") in favor of the OPEN reading, under which being
# unnamed by the enumeration decides nothing. A list ordering comparison runs
# the same elementwise walk (compareLists) that a list equality comparison
# runs (valuesEqual), and only the latter was charged -- a discrepancy
# measured at 1,666x on the same expression shape. ops.go's list/list
# ordering row now charges Cost{ArgElements: {0}}, matching applyBinary's
# equality charge exactly.
#
# The consequence for THIS file: eleven list-ordering entries stopped
# diverging and were removed, because the reference's flat 2 happens to equal
# sqi's own 1 + 1 on the one-element and empty-list operands the corpus uses.
# The list-ordering entries that remain are the ones with 2+ elements, where
# sqi's 1 + N genuinely exceeds the reference's flat 2 -- the same "sqi
# charges where the reference does not" family as the LIST/RANGE EQUALITY
# section below, and adjudicated on the identical grounds. Each says so on
# its own line.

# ── sqi is right: and/or and the conditional expression are not calls ───────
#
# RFC 0005 rule 6 states boolean operators "are handled directly by the
# evaluator (not transformed to function calls) to support value-returning
# and short-circuit semantics", and the "Expression Evaluation" pseudo-code
# evaluates IfExp (the conditional expression) the same way -- neither ever
# reaches a Call node. Section 1.3.10 rule 1 charges only "every function
# call", so an operator that is explicitly NOT transformed into one earns no
# charge under rule 1, and neither is named by rule 2 or rule 3. sqi's
# evalLogical and evalCond (eval.go) charge nothing, exactly as the spec's
# own transformation rule requires; ops.go's unaryShapes comment already
# records the and/or half of this ("RFC 0005 line 1454 says they are handled
# directly by the evaluator rather than transformed to function calls").
# The reference charges 1 for both anyway, with no basis in the spec text.

# ── sqi is right: unique() charges its real quadratic scan; reference charges only the linear input ──
#
# Task 12 decided this by RUNNING, not by reasoning about it:
# TestUnique_IsBoundedByTheOperationLimit (internal/openjd/expr/carried_internal_test.go)
# first ran against unique() charged only by a declared Cost{ArgElements: {0}}
# -- the input list's length -- and unique(range(20000)) returned
# successfully in under 4 seconds with ~4*10^8 valuesEqual comparisons

# 10-million default limit. Section 1.3.10 rule 2's own text ("when a
# function ... iterates through every element of a list, the number of
# elements is added") does not on its own capture a function that iterates
# the SAME list once per element it keeps, which is what unique's
# de-duplication scan does: Value cannot be a map key (its Type contains a
# slice) and section 1.2.5's cross-type equality is not a hashable relation,

# implementation choice that could be linear instead.

# operation limit see the real work rather than only the input length --

# granularity the actual algorithm operates at, which is more faithful to
# the rule's stated purpose ("prevents ... excessively long processing

# ── sqi is right: padding charges ONE length term; the reference now charges two ──
#
# NEW WITH openjd-expr 0.3.0 (openjd-model 0.11.3+), found on the 0.11.4 pin
# bump. It REPLACES the "zfill charges ResultBytes; the reference's own count
# does not track it" section this file used to carry: that section's single
# entry, zfill('', 3), stopped diverging and was removed on the same run that
# turned these fifteen long-agreeing cases red. The old section's claim -- "a
# non-empty base string charges a flat 2 regardless of width, matching sqi
# exactly, so most zfill cases in this corpus do NOT diverge at all" -- is
# simply no longer true of the reference.
#
# Section 1.3.10 rule 3 charges "the length OF THE VALUE divided by 256
# (rounded up)": one value per call. sqi charges the value these functions
# PRODUCE -- Cost{ResultBytes: true} on ljust/rjust/center and on all three
# zfill overloads -- so its count is 1 + ceil(len(result)/256).
#
# The reference now charges TWO length terms. Probed directly against
# openjd-model 0.11.4, one call per probe:
#
#   ljust(<300-byte literal>, 5)   3 = 1 + ceil(300/256) + ceil(0/256)
#   ljust('a', 256)                3 = 1 + ceil(1/256)   + ceil(255/256)
#   ljust('a', 257)                3 = 1 + ceil(1/256)   + ceil(256/256)
#   ljust('a', 300)                4 = 1 + ceil(1/256)   + ceil(299/256)
#   ljust('a', 600)                5 = 1 + ceil(1/256)   + ceil(599/256)
#
# -- the argument's length, PLUS the length of the padding it adds. Each term
# is individually rule-3-shaped, which is what makes this a two-value reading
# of a rule that names one value, rather than an arbitrary flat +1.
#
# The two counts CONVERGE on large inputs, because the padding added is then
# empty: ljust(<600-byte literal>, 5) is 4 on both sides. Every entry below is
# therefore a small-string case, where the argument and the padding each round
# up to a unit of their own and the reference's second term is visible.
