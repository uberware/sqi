# Accepted OPERATION-COUNT divergences between sqi's Go evaluator and the OpenJD
# reference implementation, for section 1.3.10's operation-bounded evaluation.
#
# Kept separate from baseline.txt deliberately. The two failure modes are
# independent -- a case may agree on VALUE and diverge on COUNT -- and the
# three-direction rule (an unlisted divergence is a regression, a listed case
# that stops diverging is stale, an entry matching no live result is orphaned)
# has to hold separately for each. One file could not express that.
#
# Counts are compared ONLY on cases whose values already agree. A case whose
# value diverges is already reported and already baselined; comparing its count
# too would report one root cause twice.
#
# Format: the comment lines immediately above an entry are its reason, and the
# entry itself is a case id from corpus.txt -- "<target> :: <expression>",
# exactly as the failure output prints it. A blank line separates entries. An
# entry with no reason above it is a hard error.
#
# THE SPEC OUTRANKS THE REFERENCE. Section 1.3.10 states the counting rules
# precisely, which is what makes counts comparable at all -- but openjd-expr is
# Beta and has known counting defects (center('ab', -3) has been measured failing
# with "operation count (72057594037927938) exceeded limit"). An entry here may record
# either a genuine gap in sqi or a case where sqi is right. Say which.

# ── sqi is right: the reference over-counts ordering, equality and "not" ────
#
# RFC 0005's AST-transformation table (section "AST Transformation to Uniform
# Function Calls") converts every ordering comparison (<, <=, >, >=), both
# equality operators (==, !=) and "not" into a __lt__/__le__/.../__not__ call.
# Section 1.3.10 rule 1 ("every function call counts as 1 operation") is the
# whole charge for each of these whenever its operands are SCALARS: nothing
# iterates a list and nothing processes a string byte-for-byte, so rules 2
# and 3 have nothing to charge. The reference nevertheless measures 2 for
# every ordering comparison, for "not True" and for scalar equality -- a flat
# +1 with no textual home, and the divergence every entry below records.
#
# A CHAINED comparison ("1 < 2 < 3") is section 1.3.6's single Compare node,
# evaluated as one short-circuiting unit; the reference's extra +1 is paid
# ONCE for the whole chain, not once per link -- confirmed by "1 < 2 < 3"
# measuring only 1 more than sqi's 2 (which already charges rule 1 once per
# link), not 2 more.
#
# The rule-1-only claim does NOT extend to the LIST/LIST ordering row.
# internal/openjd/expr/doc.go settles the disagreement between the two
# specification documents over whether rule 2's enumeration is open or closed
# (the wiki says "such as", RFC 0005 says "This applies to:") in favor of the
# OPEN reading, under which being unnamed by the enumeration decides nothing.
# A list ordering comparison runs the same elementwise walk (compareLists)
# that a list equality comparison runs (valuesEqual); charging only the
# latter undercounts by 1,666x on the same expression shape. ops.go's
# list/list ordering row therefore charges Cost{ArgElements: {0}}, matching
# applyBinary's equality charge exactly.
#
# On the corpus's one-element left operands, the reference's flat 2 equals
# sqi's 1 + 1, so those cases agree and are not listed. The list-ordering
# entries with 2+ elements are listed because sqi's 1 + N exceeds the
# reference's flat 2 -- the same "sqi charges where the reference does not"
# family as the LIST/RANGE EQUALITY section below, adjudicated on the same
# grounds. Each says so on its own line.

# ── sqi is right: and/or and the conditional expression are not calls ───────
#
# RFC 0005 rule 6 states boolean operators "are handled directly by the
# evaluator (not transformed to function calls) to support value-returning
# and short-circuit semantics", and the "Expression Evaluation" pseudo-code
# evaluates IfExp (the conditional expression) the same way -- neither ever
# reaches a Call node. Section 1.3.10 rule 1 charges only "every function

# ── string(list): sqi omits the reference's RESULT unit and its recursion ────
#
# openjd-rs#336 (openjd-expr 0.4.0, openjd-model 0.11.5) changed the
# reference's counting for string(list). A pin bump can invert the direction
# of a divergence without any entry going stale: the three-direction rule
# cannot see a reason going false while the divergence itself persists, so
# read the DELTAS on a bump, not just the pass line.
#
# What the reference charges, measured directly at openjd-model 0.11.5:
#
#   string([])                  2 = 1 call + 0 elements + 1 result
#   string([1])                 3 = 1 + 1 + 1
#   string([1, 2, 3, 4, 5])     7 = 1 + 5 + 1
#   string([[1], [2]])          6 = 1 + (2 outer + 2 inner) + 1
#   string([[1,2,3], [4,5,6]]) 10 = 1 + (2 outer + 6 inner) + 1
#
# -- one per element counted RECURSIVELY, plus a unit for the RESULT string.
# sqi charges rule 1 (1) plus ArgElements, the argument list's own length, not
# recursed, and nothing for the result. So sqi is BELOW the reference on
# every entry in this section.
#
# TWO divergences, adjudicated separately:
#
#   1. The RESULT unit -- sqi is right to omit it. Rule 3 charges "when a
#      function processes a string or path VALUE", which is about what goes in,
#      not what comes out. The repr_* section below records the same ruling
#      (openjd-rs#284 added result units to those five functions).
#
#   2. The RECURSION -- sqi UNDER-charges, and this half is a known gap in sqi
#      rather than a ruling in our favour. sqi's own reading of rule 2 is that
#      the general "iterates through every element of a list" clause applies
#      here because writeJSONValue walks every element; that walk descends into
#      nested lists, so the same reading charges their elements too. Closing it
#      means giving Cost.ArgElements a recursive variant, and ArgElements is a
#      shared primitive whose other rows (the five repr_*, join, and the rest)
#      each carry their own separately measured reference behavior -- changing
#      it would move all of them at once. Under-charging is the SAFE
#      direction: it can only accept an expression a limit would otherwise
#      reject, never reject a legitimate one.
#
# Rule 2's enumeration is introduced with "such as", so the general clause is
# not closed by the named list, and writeJSONValue really does walk every
# element of the list argument to render it -- confirmed against the spec text
# at third_party/openjd-specifications/wiki/2026-02-Expression-Language.md,
# section 1.3.10 rule 2. "string(flatten(...))" combines this with flatten()'s
# own charge, which the reference already matches exactly (flatten is not
# itself in this baseline).

# whole divergence here is the reference's result unit (see section header).

# ── sqi is right: padding charges ONE length term; the reference charges two ──
#
# Reference behavior since openjd-expr 0.3.0 (openjd-model 0.11.3+).
#
# Section 1.3.10 rule 3 charges "the length OF THE VALUE divided by 256
# (rounded up)": one value per call. sqi charges the value these functions
# PRODUCE -- Cost{ResultBytes: true} on ljust/rjust/center and on all three
# zfill overloads -- so its count is 1 + ceil(len(result)/256).

# The reference charges TWO length terms. Probed directly against
# openjd-model 0.11.4, one call per probe:

# The two counts CONVERGE on large inputs, because the padding added is then
