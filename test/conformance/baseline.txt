# Each line is a fixture path relative to the 2023-09 suite root, and every
# entry MUST carry a reason. An entry without one is a hard error in review:
# a bare path records that something fails without recording what, which is how
# a burn-down list decays into an ignore-list.
#
# This is a burn-down list, not an ignore-list. CI fails in THREE directions: a
# test that fails without being listed here is a regression, a listed test that
# starts passing is a stale entry that must be removed, and an entry matching no
# live result at all is orphaned. Fixing conformance defects therefore shows up
# as deletions from this file.
#
# base/env_templates/* : not listed here. sqi does not implement standalone
# environment-2023-09 templates at all, so every fixture under any
# env_templates/ directory is StateNotApplicable (see classify.go) and is
# never scored — it cannot regress or go stale, so it has no baseline entry.
#
# The three EXPR/job_templates entries below are scored by
# TestConformance_Templates like every other live directory: 206/209 pass,
# 3 baselined.
#
# All three fail for the same underlying reason, and it is not EXPR's: each
# declares FEATURE_BUNDLE_1, a separate official OpenJD extension (RFC 0004)
# that sqi does not register, so validateExtensions rejects the template on the
# extension name alone. Each also USES that extension's `bash:` SimpleAction in
# place of `script:` — the element FEATURE_BUNDLE_1 defines and sqi does not
# model — so the same fixtures additionally report a missing required `script`.
# Both errors are one gap, counted twice. All three fixtures are VALID (no
# ".invalid" suffix): the spec says accept them, sqi rejects them, so they fail.
# They come off this list when sqi implements FEATURE_BUNDLE_1, or not at all.
#
# The per-fixture errors below were MEASURED through openjd.Parse +
# openjd.ValidateWithOptions(EnforceLimits: true), not inferred from the
# filenames.
#

# Added upstream by openjd-specifications PR #172 ("do not cap <IntRangeExpr>
# expansion at the list-form limit"), which also rewrote 3.4--max-range-items.yaml
# and 3.4--too-many-range-items.invalid.yaml to use explicit LISTS of 1024 / 1025
# values (both pass here — only the range-EXPRESSION case fails).
#
# The change is a base-spec acceptance widening: §3.4's "at most 1024 values"
# bounds the LIST form only, so `range: "1-5000"` — one <IntRangeExpr> naming
# 5000 values — is valid. The normative sentence behind it is at
# wiki/2023-09-Template-Schemas.md:1155: the number of values an <IntRangeExpr>
# expands to "is not constrained by this specification", and an implementation
# needing to bound Step size "is expected to do so with its own limit on the
# Task count, not by constraining this expression". sqi has those count limits
# — maxTasksPerStep and maxTasksPerJob — so the fix is tractable, but it is a
# policy decision. sqi applies the cap to BOTH forms: taskParamValueCount
# (validate.go) counts a RangeExpr arithmetically and hands the same
# maxTaskParamValues (1024) gate the count, so the fixture is rejected on
# `/steps/0/parameterSpace/taskParameterDefinitions/0/range: at most 1024
# values are allowed per task parameter (got 5000)` — MEASURED, not inferred.
#
# Not fixed here. Lifting the cap for the expression form is an acceptance
# change in internal/openjd — templates rejected today would start producing
# tasks — and it lands on the same policy surface as maxTasksPerStep and
# maxTasksPerJob, the same reasoning that keeps internal/openjd's three
# integer-range divergences from the spec. It needs its own decision.
base/job_templates/3.4--wide-int-range-expression.yaml
