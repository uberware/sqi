# EXPR fixtures whose embedded expressions do not yet parse, or do not
# evaluate cleanly against a symbol table built from what the fixture itself
# declares.
#
# Scored by TestConformance_Expressions via conformance.RunExprCase: see the
# RunExprCase doc comment for why EXPR has a scoring path of its own and when
# to delete it. RunExprCase evaluates EVERY expression, not only a
# symbol-free one: conformance.DeclaredSymbols binds every symbol section
# 1.2.2 defines as an unresolved placeholder of its declared type, and every
# name introduced by a "let:" block as untyped (expr.TAny), so an expression
# that references a symbol is checked, not skipped. That is why fixtures like
# the expr2.1.1--int64-overflow-* group and expr2.1.1--division-by-zero left
# this list once evaluation shipped (sub-project B1, task 15) — they parse
# fine but were always rejected by the evaluator — and why a further batch of
# symbolic fixtures left it once the declared-symbol table shipped (task 16):
# a genuine type error or unknown-variable fixture now fails for real,
# rather than being reported as parse-only.
#
# Each line is a fixture path relative to the 2023-09 suite root.
#
# This is a burn-down list, not an ignore-list. CI fails in BOTH directions,
# and in a third: a fixture that fails without being listed is a regression, a
# listed fixture that starts passing is a stale entry, and an entry matching no
# live result is orphaned. All three must be fixed, not suppressed.
#
# Expect most entries to be one of two kinds, and both to burn down later:
#   - syntax the reader does not implement (comprehensions, calls, methods) —
#     sub-projects B3 and C;
#   - a fixture invalid for a reason DeclaredSymbols' flat, scope-blind table
#     cannot see: a symbol used somewhere the real template schema forbids it
#     (Session.WorkingDirectory in host requirements, Step.Name in the job's
#     own name field), a "let" binding invalid for a scoping reason (a
#     duplicate name, a self-reference, one shadowing an enclosing binding),
#     or a parameter default that fails validation against its own declared
#     type — all context this scoring path does not carry, and all still
#     sub-project E's, when templates are evaluated with real scope tracking.
#
# Note for sub-project E: expr1.3.9--memory-limit-exceeded
# ({{ 'a' * 100000000 }}) left this list in task 15 too, but NOT because a
# memory limit is enforced — §1.3.9's memory-bounded evaluation does not
# exist yet. THE MECHANISM THIS NOTE USED TO GIVE WAS WRONG, and is corrected
# here rather than quietly rewritten: it said the fixture was rejected because
# string repetition (__mul__(string, int)) was unimplemented, and predicted
# the fixture would start FAILING once repetition shipped. Repetition shipped
# in sub-project B2 — ops.go's OpMul table registers {TString, TInt} ->
# repeatString, and 'a' * 3 is "aaa" — and the fixture kept passing, because
# what actually rejects it is limits.go's hard, non-configurable
# maxStringBytes bound (10,000,000 bytes, applied by checkRepeat). The
# conclusion the old note reached still holds: this is not a §1.3.9 pass. A
# fixed per-operation ceiling is not a memory budget — an expression that
# stays just under it repeatedly still allocates without bound — so the
# configurable §1.3.9 limit remains sub-project E's, and this fixture will
# only be passing for the RIGHT reason once E lands it.
#
# THAT HAS NOW HAPPENED, exactly as written, and the note is kept rather than
# deleted because it is the record of a prediction that came true:
#
#   EXPR/job_templates/7.3--apply-path-mapping-in-job-name.invalid.yaml
#   EXPR/job_templates/7.3--apply-path-mapping-in-timeout.invalid.yaml
#
# Sub-project D registered apply_path_mapping, so these two now evaluate
# cleanly (passthrough with no rules) instead of failing "unknown function" —
# but they are .invalid because the call is placed in a submission-time context
# (a job name, a timeout) where a host-context function is forbidden. That
# placement rule needs scope-aware evaluation, which is sub-project E's; until
# then both are baselined below, and the predicted 145 -> 143 is what the
# rollup now reports. (Same class as
# expr1.3.10--string-operation-limit-exceeded.) Do not treat the regression as
# a defect in D's implementation; it is this scoring path's blind spot becoming
# visible. Deleting these two entries is E's job, not a cleanup.
#
# expr1.3.10--operation-limit-exceeded joins this list for the mirror-image
# reason, in sub-project C1's task 9: it was correctly rejected only because
# range() was unimplemented (an "unknown function" error), not because
# §1.3.10's 10-million-operation limit was enforced — that limit is still
# sub-project E's. Now that range() is registered, the fixture's triple-nested
# comprehension over range(300) parses and evaluates to completion instead,
# so it wrongly PASSES where the spec calls for rejection. Its sibling
# expr1.3.10--string-operation-limit-exceeded was noted at the time as not
# affected, because it depends on a string method call (.upper()) that was not
# registered yet, so it was still rejected for a real (if different) reason —
# that prediction has now come true: sub-project C2's string-function wave
# registers .upper(), so this sibling's comprehension now also parses and
# evaluates to completion instead of failing on an unknown function, and it
# too wrongly PASSES where the spec calls for rejection. Both entries burn
# down together only once an operation counter lands, which is still
# sub-project E's.
#
# It is kept separate from baseline.txt because the same fixture IDs appear in
# both scoring paths, and an EXPR entry there would be reported as orphaned
# forever.
