# The fix: TestConformance_Expressions now calls a small wrapper, runEXPRCase
# (suite_test.go), instead of conformance.RunCase directly. runEXPRCase runs
# the exact same Parse + ValidateWithOptions RunCase does, then DISCOUNTS
# (removes) any ValidationError that is the EXPR extension's own
# registered-but-unsupported rejection BEFORE deciding acceptance —
# discountEXPRGateErrors / isEXPRGateError, keyed structurally off the
# error's Pointer ("/extensions/<index>") plus openjd.LookupExtension's
# Status field, not message text, so a wording change to the gate's message
# does not silently stop this from working.
# TestEXPRGateFilter_MatchesRealValidateExtensionsOutput drives the real
# validateExtensions code path (not a synthetic error) to pin that pointer
# format. RunCase ITSELF is unchanged — every other suite directory keeps its
# current, unfiltered semantics, and production keeps reporting the gate
# error verbatim (TestConformance_EXPRNotSupported still checks this).
#
# This filter is temporary in exactly the way RunExprCase is: once
# sub-project H flips EXPR to StatusSupported, discountEXPRGateErrors always
# removes zero errors (there is no gate error left to discount), so
# runEXPRCase becomes indistinguishable from calling RunCase directly. H's
# checklist (TestConformance_EXPRNotSupported's failure message) now names
# runEXPRCase, discountEXPRGateErrors, isEXPRGateError and
# TestEXPRGateFilter_MatchesRealValidateExtensionsOutput for deletion
# alongside RunExprCase and this file — do not remove this filter as
# "redundant" before then; while EXPR is StatusInProgress it is load-bearing.
